# V2.1.0：服务端语音识别（SenseVoice + Silero VAD）

## 背景

V2.0.1 在测试版真机验证时，Chrome 自带识别（Web Speech API）首字延迟约 21.6 秒、定稿延迟约 38 秒，2 分钟只推送 11 次结果（见 `asrReport()` 实测）。原因在浏览器背后的识别服务，页面代码无法改善。

约束：
- 模型**不放在浏览器**，浏览器只采集音频。
- 免费、无需第三方 API Key：使用开源模型 SenseVoice-Small（int8），在我们自己的服务器上 CPU 推理。

服务器实测（2 核、无 GPU，sherpa-onnx 2.0.1）：1 线程实时率约 0.155（1 秒音频约 0.15 秒识别完），内存峰值约 390MB。

## 方案

```
浏览器 getUserMedia → AudioWorklet(asr-worklet.js) 重采样为 16k 单声道 int16
   │ WebSocket /api/asr?token=...（二进制 PCM，每块 100ms）
   ▼
Node server/index.js：校验登录 token → 逐帧转发（不解析音频）
   │ WebSocket ASR_URL（只监听 127.0.0.1:8011）
   ▼
Python asr/server.py：Silero VAD 断句 + SenseVoice 识别 → partial / final
```

### 识别协议（Node 与 Python 之间、浏览器与 Node 之间相同）

| 方向 | 消息 | 说明 |
| --- | --- | --- |
| 客户端 → | `{"type":"start","lang":"auto"}` | 开始会话 |
| 客户端 → | 二进制帧 | 16kHz 单声道 int16 小端 PCM |
| 客户端 → | `{"type":"stop"}` | 停止：把未结束的语音段识别完再回 `end` |
| ← 服务端 | `{"type":"ready"}` | 可以开始识别 |
| ← 服务端 | `{"type":"partial","seg":n,"text":...}` | 当前语音段的临时结果，会被修订 |
| ← 服务端 | `{"type":"final","seg":n,"text":...,"start":秒,"end":秒,"lang":...,"decode_ms":...}` | 语音段定稿 |
| ← 服务端 | `{"type":"end"}` | `stop` 之后的最后一条消息 |
| ← 服务端 | `{"type":"error","error":"busy"\|"upstream",...}` | 识别服务繁忙 / 不可用 |

### 断句与临时结果

SenseVoice 是整句（非流式）模型，用下面的方式模拟实时效果：
- **断句**：Silero VAD，静音 ≥ 0.5 秒（`ASR_MIN_SILENCE`）结束一段；连续说话超过 10 秒（`ASR_MAX_SEG`）由服务端在后半段最安静处强制切开（见文末变更记录 V2.1.1）。
- **partial**：语音段进行中，每新增约 0.8 秒音频（`ASR_PARTIAL_INTERVAL`）把这一段已有音频整体重识别一次。单次解码越慢，间隔自动拉长到解码耗时的 2 倍，避免 CPU 被临时结果占满。同一时刻每个连接最多一个 partial 在算。
- **final**：VAD 判定一段结束后整段识别一次。
- **pre-roll**：VAD 判定"开始说话"有延迟，段首一两个字会被吃掉。partial 和 final 都会在段首补上最多 0.4 秒之前的音频，补的范围不越过上一段的末尾，避免同一段话被识别两次。
- 迟到的 partial（它所属的段已经 final）直接丢弃。

### 前端接入（public/app.js）

- 控制栏新增「识别」下拉框 `selAsr`：服务器（推荐，默认）/ 浏览器自带。服务器未开启 `ASR_URL` 或浏览器不支持 AudioWorklet 时，"服务器"选项置灰，自动用浏览器识别。
- `partial` → 写入 `run.interim`，复用 V2.0.1 的实时文字和临时气泡；`final` → 调用现有 `commitFinal()`，翻译、入库、朗读、判重逻辑全部复用。
- 按段号 `seg` 去重：同一段的 final 只提交一次。
- **断线**：麦克风不停，音频先在浏览器缓存（最多 60 秒，`SRV_BACKLOG_MAX_MS`），重连成功后整体补发，所以短时间断线不丢音频。断线那一刻还没定稿的 partial 按"待校对"保存。重连按 0.5s、1s、2s… 退避，最长 8 秒。只有缓存溢出、真的丢了音频时才在记录里插入黄色"识别中断"提示（`asrGaps()`）。
- 连续多次连不上服务器时，自动切回浏览器自带识别。
- **手动停止**：发 `stop`，最多等 6 秒（`SRV_STOP_TIMEOUT`）拿到最后一段的 final 和 `end` 再关闭；超时则把残留 partial 按"待校对"保存。
- 诊断：`asrEvents()` 里新增 `server-end`、`backlog-sent`、`backlog-dropped`、`residual`、`error upstream` 等事件，`asrReport()` 指标沿用。

### Node 转发（server/index.js）

- `GET /api/asr/status` → `{ok:true, enabled}`，`enabled` 取决于是否配置了 `ASR_URL`。
- `WebSocket /api/asr?token=...`：用登录 token 鉴权（账号必须是 active 且已改过初始密码），失败返回 401；未配置 `ASR_URL` 返回 503。
- 上游未连上时最多缓存 8MB（约 4 分钟音频），超出则断开。上游出错时先给浏览器发 `{"type":"error","error":"upstream"}` 再关闭，浏览器进入重连。
- 每个会话结束打一行日志：用户名、时长、音频秒数。

## 部署

服务器上的目录：

| 路径 | 内容 |
| --- | --- |
| `/opt/asr/venv` | Python 3.11 虚拟环境（`pip install -r asr/requirements.txt`；CentOS 7 的 GCC 太老，numpy 必须用 `<2.3` 的二进制包） |
| `/opt/asr/models/sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2025-09-09/` | SenseVoice int8 模型（`model.int8.onnx` 约 237MB、`tokens.txt`），来自 sherpa-onnx 的 GitHub release |
| `/opt/asr/models/silero_vad.onnx` | Silero VAD 模型 |
| `/opt/asr/server.py` | 从仓库 `asr/server.py` 复制 |

```bash
# 1. 识别服务（只监听 127.0.0.1:8011，不对外）
install -m 644 asr/server.py /opt/asr/server.py
cp deploy/livetranslate-asr.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now livetranslate-asr
journalctl -u livetranslate-asr -n 20          # 看到 "ASR listening on 127.0.0.1:8011"

# 2. 打开 Node 的转发：在对应环境的 .env 里加一行，然后重启 Node
echo 'ASR_URL=ws://127.0.0.1:8011' >> /opt/livetranslate-staging/.env
systemctl restart livetranslate-staging

# 3. 冒烟测试
/opt/asr/venv/bin/python asr/stream_wav.py ws://127.0.0.1:8011 test.wav
curl -s http://127.0.0.1:8010/api/asr/status   # {"ok":true,"enabled":true}
```

nginx 已为 `location /` 设置了 `Upgrade`/`Connection` 头，WebSocket 不需要额外配置。

服务器内存紧张（可用约 700MB、原先无 swap），部署时加了 2GB swap 文件 `/swapfile` 防止 OOM；识别服务 systemd 限制 `MemoryLimit=1200M`。

关闭服务端识别：从 `.env` 删掉 `ASR_URL` 并重启 Node，前端会自动回到浏览器识别。

## 验证

本地（Chrome 无头 + 假麦克风播放 wav，脚本经 Node 转发连到本机识别服务）：
- 中文 / 英文 / 粤语三段音频全部出 final，入库并翻译；首字（第一个 partial）约 1.3～3 秒（含建连），停顿后定稿约 1.1 秒。
- pre-roll 修复前后对比：段首"早""六"等字由丢失变为保留。
- 识别中途杀掉 Python 服务 6 秒再拉起：断线时的 partial 按"待校对"保存；浏览器按 0.5/1/2/4 秒退避重连；重连后补发 7.5 秒缓存音频，后续内容完整识别；没有重复 final。
- 手动停止：最后一段在 `stop` 后约 0.3～0.9 秒拿到 final，随后 `end`。

真机验证（测试版）：
1. 打开 `https://translate.guoming576.cn/__staging`，登录，「识别」选"服务器（推荐）"。
2. 正常开会说话 10 分钟以上，期间断网 10 秒再恢复一次，最后点停止。
3. 控制台运行 `copy(JSON.stringify({e: asrEvents(300), g: asrGaps(), r: asrReport()}))` 把结果发回分析。

## 已知限制

- SenseVoice 不是逐字流式模型，临时文字靠整段重识别实现，大约每 0.8～1 秒刷新一次，不会逐字跳动。
- 英文识别有错词（测试样本中 "TRIBAL CHIEF" 被识别为 "TRIBL CHIEF"），自动语种识别对中英混说的效果还需要真机评估。
- 识别服务断线时，正在说的那一段已经发给旧服务的音频会丢失，只留下最后一次 partial（标"待校对"）。
- 并发：`ASR_MAX_STREAMS=4`，超过返回 busy；2 核服务器上同时 2～3 路会议预计可用，未压测。
- 浏览器断线缓存只在页面内存里，关闭或刷新页面会丢失。

## 变更记录

### V2.1.1：单段硬上限（修复"单句过长"）

**问题**：11-06 测试版真人会议（约 14 分钟、83 段）里，最后几分钟出现 16～23 秒的长段，单次解码涨到 2～3.5 秒，随后整台服务器卡死（详见下方"线上事件"）。原因是 Silero VAD 的 `max_speech_duration` 不是硬切：超时后只是临时调高阈值、缩短静音判定，连续说话、背景有声音时仍会放出远超 15 秒的段。段越长，partial 每次整段重识别越慢、占内存越多。本地用一段 70 秒、句间只停 0.15 秒的音频可以复现：旧代码切出 15.0 / 15.6 / 16.3 秒的段。

另外发现一个丢字问题：VAD 自己按 `max_speech_duration` 切段时，会把切口附近零点几秒判成静音，这一截不属于任何一段。`mix.wav` 里「七种变音**同**十种变调」的"同"就是这样丢的（旧代码只是碰巧在别处切开才没丢）。

**方案**（`asr/server.py`）：
- 新增 `ASR_MAX_SEG`（默认 10 秒）。当前语音段达到这个长度时，服务端在这段的后半部分按 30ms 一帧找能量最低的位置切开：前半段立即整段识别并发 final（带 `"cut": true`），后半段原样留作下一段的开头，继续出 partial。
- 当前段的音频改为从语音开始一直连续记录到现在（不再只记 VAD 判定为语音的块）。VAD 交来一段时只用它的**结束位置**：本地记录里到这个位置为止的音频出 final，之后的留给下一段。这样强制切段和 VAD 断句不会重复识别同一截音频，partial 和 final 用的也是同一份音频。
- 段首补音：新一段开始时，如果距上一段末尾不到 1 秒（`GAP_JOIN`），就把中间这一截整个补上（修复上面的"同"）；否则照旧补最多 0.4 秒的 pre-roll。补的范围都不越过上一段末尾。
- 不足 0.2 秒的尾巴不解码，直接发空 final，前端据此撤掉临时气泡。
- `stop` 时 VAD 收尾后如果还有没出 final 的音频，整段出 final 再回 `end`。
- `ASR_MAX_SPEECH`（VAD 自己的上限）默认从 15 改为 30，只作兜底，正常由 `ASR_MAX_SEG` 先切，尽量不让 VAD 自己切段。
- `deploy/livetranslate-asr.service` 增加 `ASR_MAX_SEG=10`。前端不用改：`cut` 段和普通 final 处理方式相同。

**验证**（本地，sherpa-onnx 2.0.1，`asr/stream_wav.py` 推流）：
- 70 秒连续说话音频（模型自带的 `zh/en/yue` 测试音频去掉首尾静音，间隔 0.15 秒拼接）按实时速度推送：旧代码段长 9.9 / 15.0 / 15.6 / 7.9 / 16.3 秒；新代码最长不超过 10 秒，相邻段首尾时间衔接（如 7.00→7.00、17.05→17.05），切点落在句间停顿处（如「…好出名嘅」|「佢乜嘢都冇…」），单段解码 0.3～0.8 秒，没有重复内容。
- 说话中途 stop（音频截到第 24 秒，最后一段已被强制切过一次）：剩余部分正常出 final，然后 `end`。
- 原有的混合测试音频 `mix.wav`：旧代码有一段 15.7 秒；新代码切成 7.0 / 5.9 / 8.9 秒，文字和旧代码一致，并且找回了旧代码丢掉的"同"。

**已知限制**：
- 强制切段时如果说话完全没有停顿，切点可能落在一个词中间，前后两段各识别半个词。10 秒内一般能找到换气停顿。
- partial 仍是 CPU 的大头：70 秒连续说话共约 60 次 partial，进程 CPU 时间约半个核，final 本身只占其中一小部分。在 2 核且已经很满的服务器上跑多路会议仍然吃紧。

### 线上事件（2026-11-06）

测试版启用服务端识别后，一场约 14 分钟的真人会议结束前后服务器（2 核 3.8GB）整机无响应：ping 通、SSH 握手和 HTTPS 超时，需在控制台重启。已确认：16:00～16:20 整机内存占用 95～97%，commit 约为物理内存 4.6 倍；16:24 起日志出现约 20 秒的延迟，随后 `systemd-journald` watchdog 超时。没有找到这段时间的 OOM 记录，所以"内存耗尽导致卡死"是推断。处理：`livetranslate-asr` 已停用并取消开机自启，测试版 `.env` 删除 `ASR_URL`（回到浏览器识别）；`nginx`、`docker` 设为开机自启（之前重启后不会自动起来，生产因连不上数据库容器而反复重启）。在识别服务换机器或这台机器腾出内存之前不要重新启用。
